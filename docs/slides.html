svelte × tree-sitter

the guest of honor

What is tree-sitter?

  • A parser generator + runtime (C, CLI in Rust) that turns source code into a concrete syntax tree. grammars exist for ~anything — including Svelte
  • Incremental — after an edit it re-parses only what changed. fast enough to run on every keystroke
  • Error-tolerant — broken code still yields a useful tree. essential: code is broken ~most of the time while you type
  • Queryable — S-expression patterns extract structure. highlighting, folding, outlines, structural search

Used by Zed, Neovim, Helix, GitHub code navigation…

how a grammar reaches the browser

grammar.js → .wasm

  1. grammar.jsthe Svelte grammar, described in JavaScript
  2. tree-sitter generateRust CLI emits a generated C parser
  3. parser.c → .wasmemscripten compiles it to a ~45 KB side module
  4. web-tree-sitterloads it at runtime, next to your Svelte code
// src/lib/treesitter/load.ts
await Parser.init();
const svelte = await Language.load(
	'/wasm/tree-sitter-svelte.wasm'
);
parser.setLanguage(svelte);

No build step needed here: the .wasm binaries ship prebuilt in the grammars' npm packages.

live demo · /highlight

Highlighting is a query

; highlights.scm — no regex, just patterns
(tag_name) @tag
(attribute_name) @attribute
(comment) @comment

; components are Capitalized
((tag_name) @tag.component
	(#match? @tag.component "^[A-Z]"))
  • Each @capture maps to a CSS class — that's the whole highlighter
  • Language injections: <script>, <style> and every {expression} get re-parsed by the JS / CSS grammars exactly how editors highlight .svelte files — toggle it live
  • Runes are plain identifiers to JS — one #match? paints $state Svelte-orange
live demo · /query

CSS selectors, but for syntax

; find every event handler
((attribute_name) @event
	(#match? @event "^on"))

; text inside headings only
((element
	(start_tag (tag_name) @_t)
	(text) @heading)
	(#match? @_t "^h[1-6]$"))
  • Patterns match tree shapes, not text
  • @captures pull nodes out, #predicates refine
  • Everything downstream is “just a query”: highlighting · folding · outlines · structural search · lint rules
  • Playground: edit the query, watch captures light up in the source

  • tree.edit() declares where the text changed; the next parse reuses every subtree it can prove unaffected
  • Cost tracks the size of the edit, not the file — how editors stay responsive on huge files
why svelte ♥ tree-sitter

Same philosophy, different layer

  • Svelte: don't re-render the world — update exactly the DOM that changed
  • tree-sitter: don't re-parse the world — rebuild exactly the subtrees that changed
  • Fine-grained invalidation, both sides of the keyboard
// the entire integration
let code = $state(sample);

const tree      = $derived(parse(code));
const highlights = $derived(query(tree));
const outline   = $derived(extract(tree));

// no effects, no caches, no plumbing
field notes from building it

Things I learned the hard way

  • Prebuilt WASM ships on npm. @tree-sitter-grammars/tree-sitter-svelte, tree-sitter-javascript, tree-sitter-css — no emscripten needed. the aggregate “tree-sitter-wasms” package was built with an incompatible emscripten — binaries wouldn't load in web-tree-sitter 0.26
  • Pick the maintained grammar. The old tree-sitter-svelte predates Svelte 5; the grammars-org one parses snippets, {@render}, else-if…
  • Measure before you demo. The Svelte grammar scales super-linearly with sibling count — a 4,000-line file took 2.8 s to parse cold. …which makes the 0.3 ms incremental re-parse look even better on stage
  • Validate queries in Node. Same WASM runs server-side — one script compile-checks every query in CI.
